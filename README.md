# Отчёт по триггерным рассылкам Solar Staff

Дашборд по сценариям Sendsay: воронка по каждому письму цепочки, динамика по неделям, алерты и сравнение ru / en.

Каждый день в 06:47 МСК GitHub Actions забирает статистику из Sendsay API, сохраняет её в `data/daily.json` (коммитом — так в истории git видно, как менялись цифры) и публикует страницу на GitHub Pages.

В репозиторий попадают только агрегаты по письмам: сколько отправлено, доставлено, открыто, кликнуто, отписалось. Адресов и других персональных данных нет.

## Первый запуск

1. **Settings → Secrets and variables → Actions → New repository secret**
   - `SENDSAY_LOGIN` — логин аккаунта Sendsay **Solar Staff**
   - `SENDSAY_APIKEY` — API-ключ (Sendsay → Настройки → API-ключи). Ключу достаточно прав на чтение статистики.
2. **Settings → Pages → Build and deployment → Source: GitHub Actions**.
3. **Actions → «Обновить отчёт» → Run workflow**.

Через пару минут отчёт будет по адресу `https://mtarlykova-dev.github.io/solar-email/`.

## Как поменять сценарии

Файл `config.json`:

```json
"scenarios": {
  "11": { "name": "Welcome Solar Staff", "lang": "auto" }
}
```

Сейчас в отчёте: Inbound (от квалификации до сопровождения) (17), Inbound (не удалось связаться) (7), Предотток (ОСНО) (18), INBOUND (регистрация) (3), INBOUND (демо) (1). Другие сценарии аккаунта не загружаются (`auto_discover: false`). Чтобы добавить сценарий, допишите его ID сюда.

Порядок писем берётся из номера в названии письма: «💙 ПИСЬМО 5 …», «1. …», «Письмо 1 (после демо)». У всех сценариев стоит `only_chain: true`: письма без номера (например, старые выпуски «ABM Banks» в сценарии 7) в отчёт не попадают. **Новое письмо в цепочке называйте с номером**, иначе оно не появится в отчёте.

Все письма на русском (`"lang": "ru"`), поэтому разбивки ru / en на странице нет. Если появится английская ветка, она включится сама при `"lang": "auto"`.

- ключ — ID сценария в Sendsay, номер из адреса `app.sendsay.ru/automation/workflows/<ID>` (число в конце имени выгрузки `stat_uni_…_41276.csv` — это не ID сценария);
- `product` — необязательно, по умолчанию `default_product` (Solar Staff). Если указать разные продукты, на странице появится фильтр по ним;
- `lang` — `ru`, `en` или `auto` (язык определяется по теме письма: кириллица → ru).

Сценарии, которых нет в конфиге, всё равно появятся в отчёте как «Сценарий #ID», пока `auto_discover: true`. Чтобы убрать сценарий, добавьте его ID в `exclude_scenarios`.

Порядок писем в цепочке — в `letters` у сценария: по каждому языку список фрагментов темы или названия письма по порядку. Так письмо остаётся на своём месте, даже если его переименовали в Sendsay:

```json
"11": { "name": "Welcome Solar Staff", "letters": {
  "ru": ["Добро пожаловать", "Как подключить исполнителей", "Закрывающие документы"] } }
```

Если `letters` не задан, номер берётся из начала названия («1. …», «(2) …»), а если его нет — по дате первой отправки (в отчёте такое письмо помечено «порядок не задан»). При добавлении нового письма в цепочку допишите его в `letters`.

Ориентиры для карточек писем — в блоке `benchmarks` (GetResponse, данные 2023): первое письмо цепочки сравнивается с welcome-письмами, остальные — с триггерными письмами. OR не сравнивается: открытия завышены из-за Apple Mail Privacy Protection.

Пороги алертов — в блоке `alerts`:

| Параметр | Что значит |
|---|---|
| `silence_days` | Срочный алерт, если сценарий не отправил ни одного письма за столько дней, хотя за 4 недели до этого отправлял |
| `volume_drop_ratio` | Объём за неделю упал ниже этой доли от обычного |
| `bounce_rate_max` | Ошибки доставки письма за `rate_window_days` выше порога (3%: ориентир для триггерных писем 2,4%, для welcome 4%) |
| `unsub_rate_max` | Отписки письма за `rate_window_days` выше порога (0,6%: ориентир для триггерных писем 0,38%, для welcome 0,94%) |
| `rate_window_days`, `min_events` | Окно для ошибок и отписок (14 дней) и минимум событий (3), чтобы одна отписка на малом объёме не давала алерт |
| `or_drop_ratio` | OR письма за 2 недели упал ниже этой доли от OR за 8 недель до этого |

## Загрузить данные вручную

Если API недоступен или нужна история до `start_date`: выгрузите «Экспорт» из сценария в Sendsay и загрузите zip/csv через GitHub (Add file → Upload files) в папку с ID сценария, например `imports/11/`. Workflow сам разберёт файл, добавит данные и переложит его в `imports/done/11/`.

После первого запуска в сводке workflow (Actions → запуск → Summary) есть таблица «Сценарии из Sendsay API»: какие ID пришли и какие письма в них. Если ID в API не совпали с номерами из адресов, поправьте ключи в `config.json` по этой таблице.

## Влияние на возврат лидов

Блок «Влияние на возврат лидов» показывает, сколько получателей каждой цепочки вернулись в воронку **Inbound** в течение 60 дней после любого письма цепочки. Возвратом считается любое из трёх событий:

- сделка контакта или его компании вышла из «Закрыто и не реализовано» в рабочий этап;
- у контакта или его компании создана новая сделка в Inbound;
- клиент сам вышел на связь: входящий звонок, входящее письмо или сообщение в чате.

События в первые 24 часа после первого письма цепочки не считаются, потому что письмо и сделку часто создаёт один и тот же триггер (например, регистрация). Получатели сопоставляются с контактами amoCRM по email. Чтобы отделить влияние писем, тех, кто открывал или кликал письма, сравнивают с теми, кто не открывал.

Для вернувшихся дополнительно считается, сколько из них потом дошли до успешного этапа воронки («Передача в аккаунтинг», статус 142): сделка в учитываемых воронках закрыта успешно после момента возврата, без ограничения по сроку. Воронки задаются в `conversion.pipelines` (по умолчанию Inbound), для отдельной цепочки — в `scenarios.<ID>.conversion_pipelines`.

Расчёт — `scripts/fetch_conversion.py`, настройки — блок `conversion` в `config.json`. Нужен секрет `AMO_TOKEN` (тот же долгосрочный токен amoCRM, что в отчёте по срокам). В репозиторий попадают только сводные цифры и ID сделок (`data/conversion.json`). Адреса и имена не сохраняются и не выводятся в лог.

## Пароль

Отчёт закрыт паролем. При сборке данные шифруются (PBKDF2-SHA256 → AES-256-GCM) паролем из секрета `REPORT_PASSWORD`, страница расшифровывает их в браузере. Открытый `report.json` на сайт не публикуется. Если секрета нет, сайт публикуется без данных.

Цифры отчёта (`data/daily.json`, `data/conversion.json`, `data/alerts.json`) в репозиторий больше не сохраняются: каждый запуск собирает их заново из Sendsay и amoCRM. В репозитории остаётся только `data/conversion_status.json` — технический статус без цифр по цепочкам.

Сменить пароль: обновить секрет `REPORT_PASSWORD` и перезапустить workflow. У тех, кто сохранил старый пароль, отчёт попросит ввести новый.

## Как устроено

```
config.json                  сценарии и пороги алертов
scripts/fetch_sendsay.py     Sendsay API (stat.uni) → data/daily.json
scripts/import_csv.py        ручные выгрузки → data/daily.json
scripts/build.py             алерты + сборка _site/ для Pages
site/index.html              сама страница
data/daily.json              агрегаты: день × сценарий × письмо
data/alerts.json             алерты на дату последней сборки
.github/workflows/report.yml расписание, коммит данных, публикация
```

Посмотреть страницу локально на выдуманных данных:

```
python scripts/demo_data.py
python scripts/build.py --data data/demo.json
python -m http.server -d _site 8000
```
